# Project Overview

`wicket-wp-admin-org-roster` is a WordPress admin plugin for managing organization rosters and person-to-organization relationships via the Wicket MDP (Member Data Platform) API. It provides bulk upload, validation, duplicate resolution, and sync workflows for administrators.

Ticket prefix: **AORM**. Plugin slug: **aorm**.

## Key Architectural Decisions

- **Classic PHP admin pages**: The Org Roster listing, configuration, and settings pages are standard WordPress admin pages rendered in PHP. Roster listing uses `WP_List_Table`. Settings use the WordPress Settings API. No React on these pages.
- **LogsListTable component** (`src/Admin/LogsListTable.php`): The Global Logs admin page (AORM-10.1–10.7, Phase 2 of AORM-10 — AORM-10.8's shared `ActivityLogger` helper was Phase 1). A `WP_List_Table` subclass, same architectural pattern as `RosterListTable` — no React. Columns (AORM-10.3): Date/Time, Organization, Membership Tier, Actor, Actor Type, Activity Type, Summary, Status, plus a non-sortable "Details" toggle column. Data comes from `ActivityLogTable::getGlobalEntries()` (see Database/ActivityLogTable.php above for the zero-schema-change membership_uuid resolution); `org_name`/`membership_tier` are then resolved here, once per distinct `membership_uuid` on the page, via the existing `MdpClient::getOrgMembershipDetail()` call (memoized in `$membershipDetailCache`) — falls back to the raw `org_uuid` when no name can be resolved. Sortable columns (AORM-10.6): `created_at` (default sort, newest first), `action`, `level` — `org_name`/`membership_tier` are deliberately excluded since they're resolved client-side after the SQL query runs and can't be sorted server-side (same rationale as `RosterListTable`'s `last_updated` column). Filter dropdowns (AORM-10.4 — Organization, Membership Tier, Activity Type, Status) plus a date range (AORM-10.5) render in `extra_tablenav('top')`; the Organization/Membership Tier/Activity Type options are built in `buildFilterOptions()` from `ActivityLogTable::getDistinctOrgUuids()`/`getDistinctMembershipUuids()`/`getDistinctActions()` — i.e. only from data that already has log activity, not the full MDP catalog — while Status uses a hardcoded 4-value map (`LEVEL_LABELS`) since `level` is a closed ENUM. Activity Type / Status / Actor Type labels are humanized via slug→label maps (`ACTION_LABELS`, `LEVEL_LABELS`, `ACTOR_TYPE_LABELS`) with a `humanizeSlug()` fallback (Title Case) for any value not in the map, so a future action/level added elsewhere never silently disappears from the page. The per-row expandable detail (AORM-10.7) is an inline toggle — no AJAX, no new REST endpoint: `single_row()` is overridden to render each column manually (rather than relying on `WP_List_Table::single_row_columns()`) followed by a hidden `<tr>` containing the row's raw `context` as pretty-printed JSON; a "View Details" button (`column_details()`) carries a `data-target` id, and `MenuPage::renderLogsToggleScript()` echoes one small inline `<script>` (click-event delegation, so it works across pagination without re-binding) that shows/hides the matching row. No Screen Options per-page entry is registered (unlike `RosterListTable`'s AORM-3.7) — fixed at `DEFAULT_PER_PAGE = 20`, not part of this ticket's acceptance criteria.
- **React islands (interactive workflows only)**: React is used exclusively for complex interactive screens that require real-time state management — roster detail view, upload review/validation, duplicate resolution, and sync progress. Each mounts into a `<div id="aorm-{feature}">` container on an otherwise PHP-rendered admin page. Each island has its own `@wordpress/scripts` entry point.

## REST API Namespace

All endpoints register under `wicket-aorm/v1/`. Example routes:

- `GET  /wicket-aorm/v1/rosters` — list org rosters
- `GET  /wicket-aorm/v1/rosters/{org_uuid}` — single roster detail
- `GET  /wicket-aorm/v1/rosters/{org_uuid}/{membership_uuid}/members` — paginated roster member list (AORM-4.5); response also carries `owner` (the membership owner as a member-shaped row with `is_owner: true`, or null) — the owner is excluded from `members`/`total` and pinned client-side as a sticky first row; accepts optional `?search=` (AORM-4.21) filtering to members whose name or email address contains the term, passed through to `MdpClient::getRosterMembers()` as a Ransack `filter[person_full_name_or_person_emails_address_cont]` param on the existing GET request (not the separate POST `/person_memberships/query` action used for the same purpose elsewhere in the Wicket ecosystem)
- `POST /wicket-aorm/v1/upload` — file upload + parse to staged records
- `GET   /wicket-aorm/v1/staged-records/{session_id}` — review staged rows
- `PATCH /wicket-aorm/v1/staged-records/{id}` — re-categorise a single record (AORM-8B.8); accepts `{category}` body param; valid values: `ready_to_sync`, `possible_match`, `probable_match`, `manual_update`, `discard`; stores old category as `previous_category`; 400 on invalid category, 404 on unknown id
- `DELETE /wicket-aorm/v1/staged-records/{id}` — permanently remove a single staged record (AORM-8B.9); 404 on unknown id; 200 with `{deleted: true, id}` on success
- `GET  /wicket-aorm/v1/staged/{id}/matches` — full MDP person details for each candidate in a staged record's `matched_persons` field (AORM-8B.12); employer lazy-loaded via a secondary `people/{uuid}/organizations` call; 404 on unknown id; 200 with `{staged_record_id, matches: [...]}` — matches is empty when no candidates are stored
- `PATCH /wicket-aorm/v1/staged/{id}/resolve` — save admin action from ReviewMatchModal (AORM-8B.18); accepts `{action, merge_target_uuid?}` body; valid actions: `create_new_record` (→ ready_to_sync / new_record), `manual_update` (→ manual_update), `merge_to_existing` (→ ready_to_sync / merging_to_record, merge_target_uuid required), `discard` (→ discard); stores old category as `previous_category`; clears or sets `merge_target_uuid`; 400 on invalid action or missing merge target, 404 on unknown id; 200 with `{id, action, category, record_status, previous_category, merge_target_uuid}`
- `POST /wicket-aorm/v1/uploads/{session_id}/commit` — trigger background MDP sync for a staged session (AORM-9.2); accepts `{ids: "all"|[...]}` body; `"all"` syncs every record in the session, an integer array syncs only those IDs; dispatches `SyncJobRunner::HOOK` via `SchedulerService`; also calls `ActivityLogger::markRosterSyncing()` immediately after dispatch so that a page reload between commit and job-start correctly resolves to the 'sync-progress' wizard step; stores committed IDs in a transient (`wicket_aorm_committed_ids_{sessionId}`, 24 h TTL) so `GET /sync-status` can scope its counts to the current batch; 202 `{accepted: true, session_id, ids}` on success; 404 on unknown session; 422 when ids is missing or invalid type; 400 when ids is empty array
- `GET  /wicket-aorm/v1/uploads/{session_id}/sync-status` — poll MDP sync progress for a staged session (AORM-9.28); served by `SyncStatusController`; reads the `wicket_aorm_committed_ids_{sessionId}` transient set by CommitController and passes it to `getSyncProgress()` so `total` / `pending` are scoped to the committed batch (not the entire session); falls back to counting all `category='ready_to_sync'` rows when no transient is present; 200 `{session_id, total, synced, failed, pending, percentage, is_complete, failed_records[]}` where `percentage = round((synced+failed)/total*100)` (100 when total=0), `is_complete = (pending===0)`, and `failed_records` is a list of `{id, error_details, raw_data}` entries for retry/display; 404 on unknown session; polled by React sync progress screen (AORM-9.29)
- `POST /wicket-aorm/v1/sync/{session_id}` — sync staged records to MDP

- Use nonces for all form submissions and REST requests (`wp_create_nonce()` / `wp_verify_nonce()`).

- File uploads: validate MIME type, enforce allowed extension (CSV only), use `wp_handle_upload()`.

## Dependencies & Integrations

- **wicket-wp-base-plugin**: Provides `wicket_api_client()`, `Wicket()` singleton, and MDP connection config. This plugin requires it to be active.
- **wicket-wp-account-centre**: **Required active plugin.** Provides the `WicketORM\` namespace (`PersonService`, `ConnectionService`, etc.) under `src/WicketORM/` — this functionality was migrated from the now-retired `wicket-wp-organization-roster` plugin. AORM will refuse to activate and will show an admin notice if this plugin is not active. Do not attempt to vendor or copy its classes locally — the plugin is the single source of truth. The following services are consumed directly:
  - `WicketORM\Services\PersonService::createOrGetPerson()` — used in `SyncService` to find or create a person in MDP by email before syncing.
  - `WicketORM\Services\ConnectionService::ensurePersonConnection()` — used in `SyncService` to create a person-to-org relationship (AORM-9.6). The relationship type is AORM's own `wicket_aorm_settings[relationship_type]` when set (passed as the `type` override); when empty, ConnectionService resolves `OrgManConfig` `relationships.defaults.type` itself. Note ACC's own strategies differ: Cascade/Groups use `relationships.defaults.type`, Direct Assignment uses `relationships.addition.type`.
  - `WicketORM\Services\ConnectionService::endRelationshipToday()` and `endActivePersonOrganizationConnections()` — used in `SyncService` for Replace mode and relationship removal (AORM-9.9, AORM-9.15).
  - `WicketORM\Services\Strategies\CascadeStrategy::removeMember()` — used in `MdpClient::removeRosterMembers()` (Roster Assignment tab's Remove Member action) when AORM's own `wicket_aorm_settings[roster_type]` setting is not `'direct_assignment'` (see `MdpClient::isCascadeStrategyActive()`). Delegated to entirely rather than reimplemented: under cascade, adding a member only creates a person-to-org connection (the MDP derives the resulting membership from it — see `AdminNotices::renderCascadeStrategyNotice()`), so AORM's own delete-person_membership-only removal would leave that connection active and let the MDP re-derive the membership, undoing the removal. `CascadeStrategy::removeMember()` ends every active person_membership for the org membership, ends every active person-to-org connection, strips every org role the person holds, and enforces the site's owner-removal guard (`prevent_owner_removal` in `OrgManConfig`) — a broader contract than AORM's non-cascade path (which only deletes the `person_membership` row and strips *configured* security roles). `MdpClient::isCascadeStrategyActive()` mirrors `AdminNotices::renderCascadeStrategyNotice()`'s detection — both treat `wicket_aorm_settings[roster_type]` as cascade-like whenever it is absent, unrecognised, or explicitly `SyncService::ROSTER_TYPE_RELATIONSHIP`, matching `SyncService::syncRecord()`'s own Relationship-path fallback; this mapping moved off the wicket-wp-account-centre plugin's `OrgManConfig::get()['membership']['strategy']` onto AORM's own roster_type setting (AORM-11.13), since the two settings describe the same relationship-derived-vs-directly-managed-membership distinction; `removeRosterMembersViaCascadeStrategy()` instantiates `CascadeStrategy` directly and calls it once per person UUID (continue-on-error, same `{removed, failed}` partial-success contract as the non-cascade path) — kept as a separate method rather than threading a `CascadeStrategy` dependency through `MdpClient`'s constructor, since `MdpClient` is instantiated bare (`new MdpClient()`) in ~15 places elsewhere and had no constructor before this.
  - CSV header-matching pattern (`getBulkColumnDefinitions()` + `resolveHeaderIndex()`) from `BulkMemberUploadService` — ported into `FileParserService` for flexible column aliasing (AORM-6.10).
  - The lib's configuration is injected via the `wicket/acc/orgman/config` WordPress filter (registered in the active child theme); its own services (e.g. `ConnectionService`'s default relationship type, `MembershipService`'s removal anchor) call `OrgManConfig::get()` internally and pick up that config automatically. AORM itself no longer calls `OrgManConfig::get()` directly anywhere (AORM-11.13) — the values it used to read from it (base member role, protected relationship types, roster-removal strategy) are now AORM's own `wicket_aorm_settings` fields, set on AORM's Settings page.
- **MDP API**: All person/org/relationship mutations go through the Wicket API via `wicket_api_client()`.

## Commit & Pull Request Guidelines

- Short, imperative, scope-specific commit messages (e.g., `adds staged records table migration`, `fixes upload validation for CSV headers`).
- Keep commits focused — no mixed refactor/feature changes.
- PRs should include: purpose, risk notes, test evidence, and screenshots for UI changes.
- Link the relevant AORM ticket.

## Release & Branch Workflow
All work happens on branches. `main` is locked; changes land via peer-reviewed
Pull Request (devs cross-review each other). Never commit to `main` directly, and never push or open a
PR without explicit human approval.

Merging a PR to `main` **auto-releases** via the `wicket-release-bot` GitHub
App: version bump, `CHANGELOG.md` update, git tag. Never bump versions or
create tags by hand. The bump level comes from a marker in the PR title
(squash-merge makes it the commit message): _(none)_ / `#patch` = patch, `#minor`,
`#major`, or `#norelease` (no release; use for docs/tooling-only merges).
Conventional commit prefixes (`feat:`, `fix:`, `docs:`, ...) drive changelog
grouping; a `!` (e.g. `feat!:`) flags a BREAKING change.
